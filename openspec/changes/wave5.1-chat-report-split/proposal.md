# Proposal: Wave 5.1 — 聊天简卡 + 报告分流 + 初评话术流

## What

在 **Wave 5 Chat-First** 已落地基础上，修正 Demo 测试暴露的体验问题，并锁定新一轮产品决策：

1. **聊天 vs 报告分流（方向 A）** — 对话 Tab 只展示 **headline +（仅正式评估）分数行 + 一句摘要 +「查看完整报告 →」**；全量诊断（阶段轨迹、per-case、结构卡、风险、完整 skill_summary）留在 **评估历史详情页**。
2. **初评不展示分数（C2）** — 用户可见的「初评」卡片 **不出现 DS/GM 分数**；分数与准入结论仅在 **正式评估** 简卡与历史详情中展示。
3. **取消主路径【整包确认】** — 初评终态若 **结构缺口清零 + 题型门禁通过**，系统自动 `auto_confirmed=True` 并触发 **正式评估**（`capability_full`）；用户 **无需额外点击**。
4. **初评后 LLM 白话叙事** — 由 **LuiAgent** 在初评结束后说明：无缺口 / 有缺口 / 题型未齐；有缺口时给出 **补充草案（白话）**，用户以 **自然语言确认或修改** 后才允许写入 staging（**必须先展示草案，再允许 mutation**）。
5. **工程修复** — rich_report 轮询导致 `<details>` 秒收；初评/正式/待专家 **三套简卡** payload；聊天气泡链到 `openRunDetail(run_id)`。

## Why

Wave 5 把报告塞进聊天气泡且轮询重绘 DOM，导致：

- AI 质量摘要无法展开（展开即被 3s 轮询清掉）
- 初评与正式评估卡片形态相同，用户把 **摸底分** 当成 **准入结论**
- 【整包确认】无上下文，与「结构已齐为何还要点」的预期冲突
- 历史详情已有全量报告，聊天重复渲染信息密度高、却缺 per-case 等字段

用户旅程应像对话产品：**聊天负责「发生了什么 + 下一步」；历史负责「查证据」**。

## 已锁定决策（2026-06-10 用户确认）

| 编号 | 决断 |
|------|------|
| **R1** | **方向 A**：仍 **2 Tab**（对话 + 历史）；不新增第三 Tab |
| **R2** | **C2**：初评简卡 **不展示** 双模型/综合分数 |
| **R3** | 结构+题型就绪后 **自动正式评估**；**取消主路径【整包确认】** UI；后端在触发前 **自动** `auto_confirmed=True` |
| **R4** | 有缺口：LLM **白话** 列缺口 + **补充草案**；交互 **A（纯文字）** — 用户回复「确认」或说明修改意见；**必须先展示草案再允许写入** |
| **R5** | 初评结束后的 **阶段说明** 由 **LLM 生成**（prompt 硬约束阶段/缺口/下一步）；简卡数据仍 **服务端 rich_report** |
| **R6** | **gaps 与题型门禁分叉**：仅 gaps 清零但题型未过 → 不得声称「可正式评估」 |
| **R7** | 对用户文案：**「初评」/「正式评估」**；禁止面向作者展示 degraded / capability_full / 摸底 |
| **R8** | 专家复核流程 **不变**（W5 §4.5：作者只读 → 专家视角批准/驳回 → 回作者） |

## Success Criteria

1. 初评简卡：仅有 headline + 一句摘要 + CTA；**无分数行**
2. 初评终态 LLM 消息：白话说明无缺口 / 待补充列表 + 草案（有缺口时）
3. 用户 **未** 对草案明确表示确认前，`mutation` **不得** 写入 staging
4. gaps+case_gate 通过后：**无【整包确认】**；自动出现正式评估 run；LLM 告知「正在正式评估」
5. 正式评估简卡：headline + 分数/结论行 + 摘要 +「查看完整报告 →」跳转历史详情（同 run_id）
6. 轮询期间用户展开的历史详情 **不受** 聊天轮询影响；聊天内无「秒收」折叠块
7. `pytest tests/ -x --tb=short` 全绿（≥400 + W5.1 新测试）
