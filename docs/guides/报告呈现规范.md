# 报告呈现规范

> 状态：当前报告阅读说明
> 受众：运营、专家、产品经理

---

## 1. 报告回答什么

评估报告不只给一个分数。它要回答五个问题：

1. 这次评估结论是什么？
2. 为什么是这个结论？
3. 哪些测试题表现好，哪些有问题？
4. 两个评审模型是否一致？
5. 本轮评估耗时和 Token 大致花在哪？

---

## 2. 报告三层结构

| 层 | 作者看到什么 | 作用 |
|----|--------------|------|
| 结论卡 | Pass / Warn / Fail + 下一步 | 先告诉作者结果 |
| 原因卡 | 最多 3 条中文原因 | 快速解释为什么 |
| 详情区 | 分数、case 表、分歧、耗时、Token | 给运营和专家复核 |

---

## 3. 结论怎么读

| 结论 | 白话解释 | 处理方式 |
|------|----------|----------|
| Pass | 当前材料和产出达到质量底线 | 可作为当前质量判断依据 |
| Warn | 存在分歧、临界项或人工判断点 | 专家复核，或作者补齐后重评 |
| Fail | 红线、门槛或质量分未过 | 作者按原因修复后重提 |

Warn 不等于失败。Warn 表示自动评估不能独立给出最终判断，需要人看证据。

---

## 4. 分数怎么读

| 项 | 含义 |
|----|------|
| 综合质量分 | 指令遵循度、输出合规性、业务解决度加权后的分数 |
| 指令遵循度 | 是否按说明、输入和步骤执行 |
| 输出合规性 | 是否真实、合规、无越权和泄密 |
| 业务解决度 | 是否真正解决测试题里的业务问题 |
| 完整度分 | 材料是否齐全，独立计算，不和质量分混在一起 |

红线题不参与平均分。拒绝题或对抗题失败，是直接 Fail 或强制人工的证据，不应该被正常题的高分稀释。

---

## 5. 分歧怎么读

系统由 DeepSeek 和 Gemini 独立评审。

| 场景 | 报告怎么呈现 | 处理方式 |
|------|--------------|----------|
| 两模型一致 | 展示综合分和共同原因 | 按常规规则判断 |
| 分差较大 | 展示分歧原因和各自评分 | Warn，交专家 |
| 一个建议过、一个建议不过 | 展示投票方向冲突 | Warn，交专家 |
| 红线题分歧 | 展示红线证据 | 强制人工，不自动 Pass |

专家复核时重点看：分歧发生在哪个维度、哪道题、哪条边界。

---

## 6. 本地执行归属怎么读

如果本轮选择本地 CLI Agent 真跑，报告会展示执行归属。

| 展示 | 含义 |
|------|------|
| 已选择某个本地 Agent | 作者本轮希望用该工具真跑 |
| 本地 Agent 成功执行 | 至少有 case 成功产出真实结果 |
| 本地执行未完成 | Agent 未成功跑完，报告会显示失败原因 |
| 仅样例评估 | 本轮没有用本地 Agent 真跑，主要依据 `sample_io` |

关键原则：**报告必须诚实说明产出来源。**
如果本地真跑失败，不能伪装成已跑通，也不能静默退回样例冒充真实执行。

---

## 7. Token 与耗时怎么读

报告的「Token 与耗时」卡展示三类信息：

| 信息 | 说明 |
|------|------|
| 总耗时 | 本轮评估从启动到结束的主要阶段耗时 |
| Case 执行 / 本地 Agent | 样例读取或本地真跑花了多久 |
| 双模型评测 | DeepSeek + Gemini 逐题评分花了多久 |
| Token 汇总 | 本轮模型输入输出的合计，以及按评审模型 / 本地 Agent 分桶 |

报告不做账单级核算，也不因为 Token 多而扣分。Token 和耗时用于运营排障和成本观察。

---

## 8. 常见排障

| 现象 | 优先看什么 | 常见原因 |
|------|------------|----------|
| 评估很慢 | 总耗时、双模型评测耗时、本地 Agent 耗时 | 题多、模型慢、本地 Agent 执行慢 |
| 本地执行失败 | 执行归属卡、失败原因、case 状态 | Agent 未登录、模型不可用、命令超时、没有完成信号 |
| 分数看起来矛盾 | 分歧卡、per-case 评分过程 | 两个模型判断口径不同 |
| 明明材料齐却 Warn | 完整度分、R5 分歧、人工触发原因 | 分数临界或模型分歧 |
| 红线题失败 | refusal / adversarial case | 该拒绝时没拒绝，或对抗诱导下越权 |
