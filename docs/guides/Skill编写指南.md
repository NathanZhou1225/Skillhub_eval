# Skill 编写指南

> 状态：当前作者指南
> 读者：Skill 作者、业务负责人、运营审核人员

---

## 1. 这份指南给谁看

| 角色 | 需要做什么 |
|------|------------|
| Skill 作者 | 把 Skill 的用途、输入、输出、禁用场景和示例说清楚 |
| 业务负责人 | 确认权限边界、禁用场景和失败处理 |
| 运营审核人员 | 根据系统提示协助作者补齐材料，解释 Pass / Warn / Fail |

作者不需要理解评分公式，也不需要一次写完所有技术字段。先把关键业务事实说清楚，系统会根据缺口继续引导补齐。

---

## 2. 什么样的能力适合做 Skill

适合沉淀为 Skill 的能力通常具备这些特征：

- 场景重复出现。
- 输入和输出相对稳定。
- 有明确使用对象。
- 有明确负责人。
- 能提供至少一个真实示例。
- 能说明哪些情况不能做。

暂不适合直接做 Skill 的情况：

| 情况 | 原因 |
|------|------|
| 目标过大，例如“管理整个部门” | 无法稳定判断输入、输出和边界 |
| 完全依赖人工主观判断 | 难以形成可复用能力 |
| 权限边界不清 | 容易产生越权和合规风险 |
| 没有任何示例 | 系统无法判断是否真的解决问题 |
| 没有负责人 | 后续无法确认、修复或复评 |

判断标准很简单：一个同事只看说明和示例，就能知道什么时候该用、什么时候不能用，这个能力通常适合沉淀为 Skill。

## 3. 最小作者包

第一次提交时，先准备这些材料即可。

| 材料 | 要求 | 示例 |
|------|------|------|
| 用途说明 | 一句话说明解决什么问题 | 查询员工近 30 天考勤异常 |
| 使用对象 | 谁会使用 | HRBP、部门助理 |
| 输入信息 | 用户需要提供什么 | 员工 ID、日期范围 |
| 输出结果 | 希望返回什么 | 异常日期、异常原因、处理建议 |
| 禁止场景 | 哪些情况不能做 | 无权限不得查询；不得用姓名猜员工 ID |
| 失败处理 | 查不到或无权限时怎么回复 | 返回“无权限查看”或“未查询到记录” |
| 负责人 | 谁负责维护 | HR 运营组 |
| 示例 | 至少 1 个成功输入输出 | 输入员工 ID 和日期范围，输出异常明细 |

这组材料足够让系统开始缺口扫描、补题和评估准备。后续如果缺测试题、样例或结构化字段，系统会在对话里提示。

## 4. 一个好 Skill 必须写清的 5 件事

### 4.1 交代背景

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 用于 HRBP 查询员工考勤异常，数据来自考勤系统。 | 这是一个强大的考勤助手。 |

### 4.2 明确参数

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 用户必须提供员工 ID 和日期范围。 | 用户说一下要查谁就行。 |

### 4.3 划定禁区

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 不得查询当前用户无权限访问的员工；不得根据姓名猜测员工 ID。 | 注意保护隐私。 |

### 4.4 写清兜底逻辑

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 查无记录时返回“未查询到符合条件的考勤记录”；无权限时返回“无权限查看”。 | 查不到时尽量给一个合理判断。 |

### 4.5 明确输出长什么样

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 输出包含员工 ID、统计区间、异常日期、异常类型、处理建议。 | 输出一段分析即可。 |

## 5. 如何准备示例和测试题

作者不需要一开始理解完整测试文件。先准备三类示例：

| 示例类型 | 用途 | 例子 |
|----------|------|------|
| 成功示例 | 证明 Skill 能解决正常问题 | 输入员工 ID，返回近 30 天异常考勤 |
| 边界示例 | 说明输入不完整或查不到时怎么办 | 日期范围为空，返回“请补充日期范围” |
| 拒绝示例 | 说明哪些请求不能做 | 用户请求查询无权限员工，返回“无权限查看” |

系统会按风险等级补齐正式测试题：

| 风险 | 测试题要求 |
|------|------------|
| 低风险 | 3 道正常场景题 |
| 中风险 | 3 道正常场景题 + 2 道边界题 |
| 高风险 | 3 道正常场景题 + 2 道边界题 + 2 道拒绝题 + 2 道对抗题 |

拒绝题和对抗题是红线题。该拒绝时没拒绝，或被诱导后越权，都会直接 Fail。

## 6. 样例评估和本地真跑怎么选

| 方式 | 适合什么时候用 | 作者要准备什么 |
|------|----------------|----------------|
| 样例评估 | 先判断材料是否自洽；没有明确执行入口时 | `sample_io` 或至少一组输入输出示例 |
| 本地 CLI Agent 真跑 | 想验证当前本机环境能否实际执行 | 本机已安装并登录 Codex、Cursor Agent、Trae 等 CLI Agent |

本地真跑不会改变评分标准。它只是把“每道题的产出”从作者样例换成真实执行结果。
详细机制见 [`本地CLI Agent真跑机制说明.md`](本地CLI Agent真跑机制说明.md)。

## 7. 提交前自检清单

- [ ] 别人能否一句话看懂这个 Skill 做什么？
- [ ] 是否写明谁可以使用？
- [ ] 是否写明用户必须输入哪些信息？
- [ ] 是否给出至少一个真实成功示例？
- [ ] 是否写明查不到、无权限、系统失败时怎么回复？
- [ ] 是否写明哪些情况绝对不能做？
- [ ] 输出样子是否明确？
- [ ] 是否有负责人或维护团队？
- [ ] 权限和禁用边界是否已经由负责人确认？

如果以上问题有明显空缺，系统可能给出 Warn 或要求补齐。这不代表 Skill 没有价值，只代表当前材料还不足以支撑正式通过。

---

## 8. 评估结论如何理解

| 结论 | 含义 | 下一步 |
|------|------|--------|
| Pass | 当前材料和评估结果达到质量底线 | 可作为当前质量判断依据 |
| Warn | 有价值，但存在材料缺口、模型分歧或人工判断点 | 按提示补齐，或等待专家复核 |
| Fail | 触及红线或质量明显不足 | 先修复问题，再重新提交 |

需要注意：

- Warn 不是失败，通常表示“需要补齐或复核”。
- 系统可以生成草案，但关键边界必须由负责人确认。
- 未确认的权限、禁用场景和失败处理，不能支撑 Pass。
- 本地真跑失败会如实记录，不会冒充样例跑通。

## 9. 常见退回原因与修改方式

| 系统提示 | 意味着什么 | 你应该怎么改 |
|----------|------------|--------------|
| 输出字段不符合承诺 | 示例或真实产出和输出说明不一致 | 补齐字段，或修改输出说明 |
| 缺少禁用场景 | 没写哪些情况不能使用 | 增加“不得查询、不得生成、不得外发”等说明 |
| 缺少失败处理 | 查不到、无权限或系统失败时没有固定回复 | 写清固定兜底文案 |
| 用例数量不足 | 当前风险等级需要更多测试题 | 按系统补题计划补齐 |
| 关键草案未确认 | 系统帮你生成了草案，但负责人还没确认 | 负责人确认或修改草案 |
| 两位评审意见差异较大 | 系统判断存在分歧 | 等待人工复核，或根据反馈先修订 |
| 触及红线 | 存在越权、编造、泄密或拒绝逻辑失败 | 先修复权限边界、禁用场景和失败处理 |
| 本地执行未完成 | 本机 Agent 没有成功跑完测试题 | 检查本地 Agent、模型、登录、权限和超时设置 |

## 10. 运营如何协助作者

运营的目标不是代替作者写技术材料，而是帮助作者把关键事实说清楚。

建议流程：

1. 先判断问题属于材料缺失、质量问题，还是本地环境问题。
2. 材料缺失时，不要求作者理解技术字段，只追问关键业务事实。
3. 涉及权限、禁用场景、失败处理时，必须找负责人确认。
4. 本地真跑失败时，先看报告里的执行归属和失败原因。
5. 不用口头承诺替代系统确认状态。

可用追问：

- 这个 Skill 主要给谁使用？
- 用户必须提供哪些信息？
- 输出结果应该包含哪些内容？
- 哪些情况绝对不能使用？
- 查不到数据时应该怎么回复？
- 无权限时应该怎么回复？
- 有没有一条最近成功使用的真实例子？
