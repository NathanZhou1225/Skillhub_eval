# Skill 编写指南

> 版本：**v1.0**  
> 读者：Skill 作者、业务负责人、运营审核人员  
> 定位：帮助业务人员用最少材料提交可评估、可补齐、可上架的 Skill。  
> 配套文档：评估/上架协议 v0.5、评估指标与准入标准 v1.2.1、评审 Agent 架构契约 v0.2。

---

## 0. 这份指南给谁看

这份指南面向三类角色：

| 角色 | 需要做什么 |
|------|------------|
| **Skill 作者** | 说明 Skill 做什么、谁来用、需要什么输入、返回什么结果、哪些情况不能做。 |
| **业务负责人** | 确认权限边界、禁用场景、失败处理和关键草案。 |
| **运营审核人员** | 根据系统提示协助作者补齐材料，统一解释 `pass` / `warn` / `fail`。 |

作者不需要理解评分公式，也不需要一次性写完所有技术字段。日常提交先满足**最小作者包**；上架前，平台会根据缺口清单引导补齐。

---

## 1. 什么样的能力适合做 Skill

适合做 Skill 的能力，通常具备以下特征：

- 有明确、重复出现的业务场景。
- 输入和输出相对稳定。
- 有明确负责人或维护团队。
- 能提供至少一个真实使用示例。
- 能说明哪些情况不能使用。

暂不适合直接做 Skill 的情况：

| 情况 | 原因 |
|------|------|
| 目标过大，例如“帮我管理整个部门” | 无法稳定判断输入、输出和边界。 |
| 完全依赖人工主观判断 | 难以形成可复用能力。 |
| 权限边界不清 | 可能产生越权和合规风险。 |
| 没有任何示例 | 平台无法判断是否真的解决问题。 |
| 没有负责人 | 后续无法确认草案、修复问题或处理复评。 |

判断标准很简单：如果一个同事只看说明和示例，就能知道什么时候该用、什么时候不能用，这个能力通常适合沉淀为 Skill。

## 2. 作者最少需要提交什么

日常提交或存量 Skill 梳理时，先提供以下材料即可。

| 材料 | 要求 | 示例 |
|------|------|------|
| 用途说明 | 一句话说明解决什么问题 | 查询员工近 30 天考勤异常。 |
| 使用对象 | 谁会使用 | HRBP、部门助理。 |
| 输入信息 | 用户需要提供什么 | 员工 ID、日期范围。 |
| 输出结果 | 希望返回什么 | 异常日期、异常原因、处理建议。 |
| 禁止场景 | 哪些情况不能做 | 无权限不得查询；不得用姓名猜员工 ID。 |
| 失败处理 | 查不到或无权限时怎么回复 | 返回“无权限查看”或“未查询到记录”。 |
| 负责人 | 谁负责维护 | HR 运营组。 |
| 示例 | 至少 1 个成功输入输出 | 输入员工 ID 和日期范围，输出异常明细。 |

这组材料称为**最小作者包**。它不等于完整上架材料，但足够让平台开始缺口扫描、降级评估和交互补齐。

## 3. 一个好 Skill 必须写清的 5 件事

### 3.1 交代背景

说明这个 Skill 服务谁、连接什么系统、解决什么问题。

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 用于 HRBP 查询员工考勤异常，数据来自考勤系统。 | 这是一个强大的考勤助手。 |

### 3.2 明确参数

写清用户必须提供哪些信息，格式是什么。不要让 AI 猜姓名、猜时间、猜部门。

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 用户必须提供员工 ID 和日期范围；日期范围只能是近 7 天或近 30 天。 | 用户说一下要查谁就行。 |

### 3.3 划定禁区

写清哪些数据不能查、哪些动作不能做、哪些请求必须拒绝。

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 不得查询当前用户无权限访问的员工；不得根据姓名或昵称猜测员工 ID。 | 注意保护隐私。 |

### 3.4 写清兜底逻辑

查不到数据、无权限、系统失败时，要有固定回复。不得编造数据补齐。

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 查无记录时返回“未查询到符合条件的考勤记录”；无权限时返回“无权限查看该员工信息”。 | 查不到时尽量给一个合理判断。 |

### 3.5 明确输出长什么样

说明输出是表格、摘要、清单、文案还是结构化字段。最好给一个标准输出示例。

| 推荐写法 | 不推荐写法 |
|----------|------------|
| 输出包含员工 ID、统计区间、异常日期、异常类型、处理建议。 | 输出一段分析即可。 |

作者只要把这 5 件事写清楚，平台后续补齐字段和评估会顺畅很多。

## 4. 如何准备示例和测试用例

作者不需要一开始理解完整测试文件。先准备 3 类示例即可。

| 示例类型 | 用途 | 例子 |
|----------|------|------|
| 成功示例 | 证明 Skill 能解决正常问题 | 输入员工 ID，返回近 30 天异常考勤。 |
| 边界示例 | 说明输入不完整或查不到时怎么办 | 日期范围为空，返回“请补充日期范围”。 |
| 拒绝示例 | 说明哪些请求不能做 | 用户请求查询无权限员工，返回“无权限查看”。 |

不同风险的 Skill，对示例要求不同：

| 类型 | 示例要求 |
|------|----------|
| **低风险** | 至少有成功示例和一个边界示例。适合文本整理、格式转换、公开资料总结。 |
| **中风险** | 必须写清权限、边界和拒绝示例。适合内部数据查询。 |
| **高风险** | 必须提供更多异常和拒绝示例。适合涉及写入、外发、敏感数据的 Skill。 |

存量 Skill 可以先用现有示例做**降级评估**。降级评估的结论最高为 `warn`，用于摸底质量和发现缺口；补齐并确认后再完整复评。

## 5. 上架前自检清单

提交完整评估前，请先自检：

- [ ] 别人能否一句话看懂这个 Skill 做什么？
- [ ] 是否写明谁可以使用？
- [ ] 是否写明用户必须输入哪些信息？
- [ ] 是否给出至少一个真实成功示例？
- [ ] 是否写明查不到、无权限、系统失败时怎么回复？
- [ ] 是否写明哪些情况绝对不能做？
- [ ] 输出样子是否明确？
- [ ] 是否有负责人或维护团队？
- [ ] 关键边界是否已经由负责人确认，而不是由 AI 自动猜测？

如果以上问题有明显空缺，系统可能给出 `warn` 或要求补齐。这不代表 Skill 没有价值，只代表当前材料还不足以直接上架。

## 6. 评估结论如何理解

平台评估后会给出三类结论。

| 结论 | 含义 | 下一步 |
|------|------|--------|
| `pass` | 当前材料和评估结果满足上架要求。 | 可进入试用或上架。 |
| `warn` | Skill 可能有价值，但材料、边界或评审判断存在不确定。 | 按提示补齐，或等待人工复核。 |
| `fail` | 触及底线问题，当前不能上架。 | 先修复红线或结构问题，再重新提交。 |

需要注意：

- `warn` 不是失败，通常表示“需要补齐或复核”。
- 平台可以生成草案，但关键边界必须由负责人确认。
- 未确认的草案不能支撑 `pass`。
- 人工复核不能绕过未确认边界直接上架。

## 7. 常见退回原因与修改方式

系统提示会尽量用可理解的语言表达。作者和运营可按下表处理。

| 系统提示 | 意味着什么 | 你应该怎么改 |
|----------|------------|--------------|
| 输出字段不符合承诺 | 示例输出和你声明的输出样子不一致。 | 补齐缺失字段，或修改输出说明。 |
| 缺少禁用场景 | 没写哪些情况不能使用。 | 增加“不得查询、不得生成、不得外发”等说明。 |
| 缺少失败处理 | 查不到、无权限或系统失败时没有固定回复。 | 写清固定兜底文案。 |
| 用例数量不足 | 当前风险等级需要更多示例。 | 增加成功、边界、拒绝示例。 |
| 关键草案未确认 | 平台帮你生成了草案，但负责人还没确认。 | 负责人确认或修改草案。 |
| 两位评审意见差异较大 | 系统判断存在分歧。 | 等待人工复核，或根据反馈先修订。 |
| 触及红线 | 存在越权、编造、敏感数据或拒绝逻辑失败。 | 先修复权限边界、禁用场景和失败处理。 |
| 评估等级不足 | 当前材料只能做初步评估，不能支撑上架。 | 补齐示例、脚本或可执行材料后复评。 |

运营可根据系统提示定位问题，但不得用口头承诺替代负责人确认。

## 8. 运营如何协助作者补齐

运营的目标不是代替作者写完整技术材料，而是帮助作者把关键事实说清楚。

建议流程：

1. 先判断问题属于**材料缺失**还是**质量问题**。
2. 材料缺失时，不要求作者理解技术字段，只追问关键业务事实。
3. 涉及权限、禁用场景、失败处理时，必须找负责人确认。
4. 对存量 Skill，先接受降级评估，再引导补齐。
5. 不用人工口头承诺替代系统确认状态。

运营可使用以下追问：

- 这个 Skill 主要给谁使用？
- 用户必须提供哪些信息？
- 输出结果应该包含哪些内容？
- 哪些情况绝对不能使用？
- 查不到数据时应该怎么回复？
- 无权限时应该怎么回复？
- 有没有一条最近成功使用的真实例子？

## 9. 可复制模板

### 9.1 最小作者包模板

```markdown
# Skill 名称

## 这个 Skill 做什么
（一句话说明用途）

## 谁会使用
（角色 / 团队）

## 用户需要提供什么
- 信息 1：
- 信息 2：

## 输出结果是什么
（说明返回表格、摘要、清单或字段）

## 不能做什么
- 禁止场景 1：
- 禁止场景 2：

## 失败时怎么回复
- 查不到数据：
- 无权限：
- 系统失败：

## 成功示例
输入：
输出：

## 负责人
负责人 / 团队：
```

### 9.2 进阶版 `SKILL.md` 模板

适合运营或高阶作者在上架前补齐。

```markdown
---
name: query_employee_attendance
display_name: 查询员工考勤
version: 0.1.0
owner: hr-ops
category: 人力资源/考勤
description: 查询指定员工在指定日期范围内的考勤记录，并返回异常摘要。
execution_mode: sample_only
risk_level: medium
permissions:
  data_scope: department_only
  requires_user_identity: true
negative_prompts:
  - 不得查询当前用户无权限访问的员工。
  - 不得根据姓名、昵称或同音字猜测 employee_id。
error_handling:
  not_found: 返回 EMPLOYEE_NOT_FOUND，不得编造员工信息。
  permission_denied: 返回 PERMISSION_DENIED，并说明需要授权。
---

# 查询员工考勤

## 使用场景
用于 HRBP 或部门助理查询指定员工在指定日期范围内的考勤异常。

## 输入要求
- employee_id：员工唯一 ID，不接受姓名猜测。
- date_range：查询范围，例如 last_7_days 或 last_30_days。

## 输出要求
返回员工 ID、统计区间、异常日期、异常类型和处理建议。

## 禁止事项
- 不得查询无权限员工。
- 不得编造员工信息。
- 不得输出未授权的敏感字段。

## 示例
输入：
{
  "employee_id": "E123",
  "date_range": "last_30_days"
}

输出：
{
  "employee_id": "E123",
  "period": "last_30_days",
  "abnormal_days": ["2026-05-12"],
  "summary": "存在 1 天迟到记录。"
}
```

## 10. Golden Case 规划

Golden Case 是给作者“照着写”的标准样例。首批建议覆盖三类。

### 10.1 数据查询类

适用：查询考勤、库存、客户状态、项目进度。

```markdown
这个 Skill 用于【角色】查询【对象】的【信息】。
用户必须提供【字段 1】和【字段 2】。
系统只能返回【允许返回的字段】。
如果用户没有权限，返回【固定回复】。
如果查不到数据，返回【固定回复】。
不得根据【姓名/昵称/模糊描述】猜测 ID。
```

重点：

- 参数必须明确。
- 权限必须明确。
- 查不到和无权限必须有固定回复。

### 10.2 文本生成类

适用：生成周报、会议纪要、客户邮件、公告草稿。

```markdown
这个 Skill 用于根据【输入材料】生成【文档类型】。
用户必须提供【素材来源】和【目标受众】。
输出应包含【结构要求】。
不得编造输入材料中没有的信息。
如果素材不足，返回【固定回复】并提示需要补充什么。
```

重点：

- 写清输入素材来源。
- 写清文风和结构。
- 禁止编造事实。

### 10.3 流程审批类

适用：发起申请、检查材料、生成审批摘要。

```markdown
这个 Skill 用于帮助【角色】整理【流程名称】所需材料。
用户必须提供【申请信息】和【附件/证明】。
系统只做【整理/校验/摘要】，不代替审批人做最终决定。
如果材料缺失，返回【缺失清单】。
如果无权限发起，返回【固定回复】。
```

重点：

- 不能代替审批人做最终决定。
- 必须说明缺材料时怎么处理。
- 必须保留来源和责任边界。

## 附录：术语对照

| 术语 | 普通解释 |
|------|----------|
| 最小作者包 | 作者先提交的最少材料。 |
| 可评估包 | 平台可以完整评估的材料。 |
| 降级评估 | 材料不完整时先摸底，最高 `warn`。 |
| 草案 | 系统帮你生成但还没确认的内容。 |
| 确认 | 负责人确认草案可作为正式边界。 |
| 红线 | 一旦触发就不能上架的问题。 |
| 人工复核 | 系统不确定时由运营或负责人判断。 |
| 复评 | 修改或补齐后重新评估。 |
